# Data

## The real data is not here

The dissertation used ball-by-ball records from the men's competition of The Hundred (2023, 2024 and 2025 seasons: 18,260 deliveries, 86 matches, 140+ columns). They were supplied by Hampshire Cricket Club, sourced through Play Cricket, under a data sharing agreement that allows use for the project but not redistribution. Player names were removed before the data was provided.

Nothing derived at delivery level from that data is committed to this repository. The README figures are drawn only from aggregate numbers already published in the dissertation's tables.

## The synthetic sample

[`sample/synthetic_raw.csv`](sample/synthetic_raw.csv) is a stand-in generated by [`src/shotzones/synthetic.py`](../src/shotzones/synthetic.py):

```bash
python -m shotzones.synthetic --matches 12 --seed 42 --out data/sample/synthetic_raw.csv
```

It has 12 matches (four per season), 2,442 rows and 74 columns. The column names and value types follow the real export for every column the pipeline uses. The cricket is invented: shot direction depends on line, length and batting hand, aggression rises in the last 20 balls, and runs depend on how far the ball travels. It is realistic enough to exercise every stage, and nothing more.

It deliberately reproduces the three defects documented in the dissertation, so the repair and cleaning code has real work to do:

| Defect | Real export | Synthetic sample |
|---|---|---|
| Five-column shift | All 2023 and 2024 rows; five columns inserted at position 105 | All 2023 and 2024 rows; five columns inserted at `PitchX` |
| Fingerprint | `Kookaburra` / `White` in `Pitchside Fielder 2 Y` / `3 X` | Same |
| Not-hit deliveries with coordinates | 1,798 rows near the keeper at (175, 120) | Roughly one row in eight, near (175, 120) |
| Fielder coordinates | 2025 only, 33.5% of those deliveries | Same proportions |
| Scattered missing values | Target, tracking, `Delivery` (16%) | Similar rates |

## Columns used by the pipeline

| Group | Columns | Role |
|---|---|---|
| Identifiers | `Match`, `Date`, `Innings`, `Innings Ball`, `Batter ID`, `Bowler ID`, teams | Grouping and ordering only, never features |
| Target source | `FieldX`, `FieldY` | Landing position on a 0-350 grid, clustered into zones |
| Delivery description | `Bowler Type`, `Line`, `Length`, `Delivery`, `Around the Wicket`, `Keeper Up`, `Free Hit` | Features (one-hot or 0/1) |
| Ball tracking | `PitchX/Y`, `ImpactX/Y/Z`, `PastX/Y/Z`, `ReleaseX/Y/Z`, `ReleaseAccelerationY/Z`, `Speed`, `SwingAngle`, `DropAngle`, `BounceAngle`, `ReleaseAngle`, `Deviation` | Features |
| Match state | `Cumulative Batter Runs`, `Cumulative Batter Balls`, `Team Runs`, `Team Wickets`, `Req Run Rate At Start` | Features, **only if recorded before the ball** (see below) |
| Fielders | `Pitchside Fielder 1..9 X/Y` | Features, `-1` where absent |
| Outcomes | `Runs`, `Extra Runs`, `Shot`, `Connection`, `Wicket`, `Ball Outcome`, `Feet` | Evaluation only, never features |

`Feet` (the batter's foot movement) is excluded as a conservative guard: it happens in response to the delivery and cannot be cleanly separated from the shot.

## Checking running totals

A running total that already includes the current ball leaks the outcome into the model. `shotzones.features.check_cumulative_timing()` compares each change in the total with the runs off the current and the previous ball, and the pipeline writes the result to `01_cumulative_timing_check.csv` before anything else. On the synthetic sample both totals are pre-ball by construction.
